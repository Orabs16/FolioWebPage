02 / 3D VOXEL PATHFINDING

3D Voxel

A custom navigation system for Unity designed to let agents navigate freely through 3D space — including walls, ceilings and fully volumetric environments.

PROJECT VIDEO / DEMO
02 / THE QUESTION

How can an agent navigate in true 3D?

Unity's standard navigation workflow is built around NavMesh surfaces and is primarily suited to characters moving across floors. That becomes restrictive when a creature needs to climb walls, walk on ceilings, fly, swim or otherwise move through a volumetric environment.

I wanted to build a reusable pathfinding system from scratch that treats the environment as a 3D volume instead of a mostly horizontal surface.

The goal was not only to make it work, but to make the system practical for real-time use: asynchronous pathfinding, Burst-compiled jobs and a compact representation of the navigable space.

04 / VOXEL BAKING

A 3D grid instead of a navigation mesh.

The first step is deciding which parts of the volume an agent can actually occupy. The tool samples the bake volume as a 3D voxel grid and uses Unity Physics queries to test each voxel against the environment.

A voxel is considered navigable when there is enough free space for the agent and it satisfies the configured distance-from-wall constraint. This makes the system useful for creatures that need to remain attached to nearby surfaces rather than simply moving through empty space.

VOXEL SIZE

Smaller voxels increase spatial resolution and allow tighter paths around geometry, but also increase bake time and memory usage.

WALL DISTANCE

A configurable maximum distance from nearby geometry controls how closely an agent can stay to a wall or other navigable surface.

05 / DATA STRUCTURE

64 voxels inside one number.

A full 3D grid can become expensive very quickly. Instead of storing one boolean per voxel, the system packs walkability into 64-bit values.

Each grid cell represents a 4 × 4 × 4 block of fine voxels. The 64 walkable states are stored inside a single ulong, turning the grid into a compact bitfield representation.

4 × 4 × 464 sub-voxelsOne coarse grid cell
→
64 BITS1 × ulongOne bit per fine voxel
→
COMPACTDense storageLess memory per voxel state

The trade-off is deliberate: the representation is slightly more complex to access, but it makes large volumetric grids much more practical than a naive boolean-per-voxel approach.

06 / A* PATHFINDING

A* running directly in 3D.

The actual path search is implemented from scratch as a Burst-compiled Unity Job. Instead of relying on a managed collection or repeatedly sorting a list, the open set uses a custom binary min-heap.

The search supports all 26 neighbouring directions around a voxel, allowing movement along diagonals as well as through the three spatial axes.

01

Binary min-heap

Keeps the lowest-cost node accessible while maintaining O(log n) insertion and removal.

02

26 neighbours

The search is volumetric rather than limited to 4- or 6-directional grid movement.

03

Euclidean heuristic

Distance to the goal provides the heuristic used to prioritize promising nodes.

07 / PERFORMANCE

Keeping the search away from the main thread.

Pathfinding can become expensive when multiple agents request paths at the same time. To avoid blocking gameplay, path requests are scheduled asynchronously through Unity's Job System.

The hot path is Burst-compiled and works with native Unity collections. Once the job completes, the result is returned to the agent through the asynchronous callback workflow.

JOBS

Asynchronous search

Pathfinding work can execute outside the main thread, reducing frame-time interruptions.

BURST

Compiled hot path

The A* implementation is Burst compiled for performance close to native code.

NATIVE

Native collections

The system uses Unity native containers so the data can be safely processed by jobs.

08 / EDITOR TOOLING

Making a technical system usable.

A pathfinding algorithm is only useful to artists and designers if configuring it is straightforward. I therefore built custom Unity editor tooling around the system instead of exposing everything as raw component properties.

The bake volume can be resized directly in the Scene view using custom handles, while a dedicated PathFinding editor window exposes voxel size, wall distance and the bake command.

The example agent snaps its position and target to the nearest walkable voxel, requests a path asynchronously and follows the returned points at a constant speed.

When the target moves, the agent can periodically refresh its path. Orientation follows the current path direction, with additional geometry awareness used for banking near obstacles.

10 / DATA PERSISTENCE

Bake once. Reuse the result.

Baking a 3D navigation volume can be expensive, so the generated grid is stored in a ScriptableObject asset rather than being rebuilt every time the project reloads.

The packed voxel data is persisted alongside the voxel size so the baked navigation volume can be restored without repeating the full physics sampling process.

12 / FUTURE DEVELOPMENT

From a static navigation grid to a living navigation system.

The current system is designed around a baked navigation volume. The next step would be to make the navigation data more modular, reusable and responsive to changes in the environment.

01

Multiple grids + bridges

Split large environments into independent voxel grids and connect them through explicit bridges. This would allow different navigation volumes to be updated or streamed independently while still behaving as one navigation network.

02

Exportable pathfinding splines

Convert generated paths into spline data that can be exported and reused by other systems. This could connect the pathfinding tool with animation, camera systems, procedural motion or designer-authored movement.

03

Live obstacle reaction

Detect changes caused by moving objects and update the affected navigation data without requiring a complete world rebake. This would make the system suitable for environments that change during gameplay.

NEXT Modular connected grids
THEN Reusable path data
GOAL Dynamic navigation
13 / WHAT I LEARNED

Designing the data matters as much as the algorithm.

The biggest challenge was not implementing A* itself. It was designing a representation of the world that could make a volumetric search practical.

The project pushed me to think about the whole pipeline: how physical geometry becomes data, how that data is stored, how the algorithm accesses it, and how the result can be exposed through tooling without making the system painful to use.

14 / LONG-TERM GOAL

A navigation toolkit built for complex 3D worlds.

The long-term direction is to evolve the prototype from a static voxel pathfinder into a modular navigation framework capable of handling large, changing and fully three-dimensional environments.
