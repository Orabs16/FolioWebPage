01 / AGENTSOLVER

Physically Simulated
Procedural Animation

An Unreal Engine plugin exploring reinforcement learning for physically simulated animation, built around a custom articulated-body physics solver and an authoring workflow for a multi-limbed creature.

ENGINE Unreal Engine 5.6
LANGUAGE C++
FOCUS Physics · RL · Tech Animation

02 / THE QUESTION

What if animation was learned from physics?

Instead of explicitly authoring every movement, I wanted to explore whether a creature could learn to control its own physically simulated body.

The project combines a custom articulated-body physics solver, muscle and mass authoring tools, and reinforcement learning through Unreal Engine's Learning Agents framework.

The first objective is deliberately simple: teach the creature to remain upright and balanced before attempting locomotion.

04 / MUSCLE & MASS AUTHORING

Turning a skeletal mesh into a physical creature.

A real skeletal mesh is not immediately usable by the custom physics solver. I built an editor workflow for defining the mass and muscle properties that connect the animation skeleton to the physical representation.

Muscles use authored extension/flexion strength curves rather than relying only on a constant torque value, giving the physical model a more useful relationship between joint angle and available force.

05 / CUSTOM PHYSICS

A physics solver built for batched simulation.

The training environment needs to simulate many creatures repeatedly. Rather than using a general-purpose constraint setup, I implemented a reduced-coordinate Featherstone Articulated Body Algorithm from scratch in C++.

The current topology contains a floating 6-DOF root followed by 3-DOF ball joints and 1-DOF yaw joints, resulting in 41 bodies and 68 degrees of freedom.

01

Reduced coordinates

The articulated body is represented through joint coordinates rather than independent constrained bodies.

02

Featherstone ABA

The solver uses an O(n) articulated-body formulation without explicitly constructing the full mass matrix.

03

Data-oriented state

Simulation state uses a Structure-of-Arrays layout designed for processing many identical environments.

06 / BATCHED SIMULATION

Thousands of environments. One solver.

Reinforcement learning becomes expensive when every training environment is simulated independently. The solver therefore processes multiple environments using the same topology and data layout.

The hot path includes an AVX2 8-wide SIMD implementation, while the environments are distributed across parallel jobs. A scalar implementation is maintained as a reference for parity checks against the optimized solver.

AVX2

8-wide SIMD

Identical simulation work is processed across SIMD lanes to reduce the cost of each physics step.

07 / CONSTRAINT SOLVER

From individual constraints to a global system.

The constraint system evolved during development. An initial per-row Gauss-Seidel approach was replaced by a globally assembled system containing ground contact, joint limits and limb collision constraints.

The resulting system is solved using Projected SOR. The assembled matrix is constructed without explicitly forming the mass matrix by reusing an existing impulse-response query.

CONTACT Ground Contact constraints
LIMIT Joints Joint-limit constraints
COLLISION Limbs Self-collision constraints
→
A = JMJᵀ + R Global system Projected SOR

The new approach was not only cleaner conceptually: profiling showed it to be approximately 1.57× cheaper than the previous per-row solver.

08 / REINFORCEMENT LEARNING

Learning to stay upright before learning to walk.

The learning layer uses Unreal Learning Agents with PPO. The policy receives information about the creature's physical state and produces a normalized action for every controllable degree of freedom.

Observations currently include torso orientation and velocity, height error, joint positions and velocities, and contact information. The reward encourages survival, upright posture and balance while penalizing excessive torque.

Locomotion is intentionally not part of the current objective. Standing is the first milestone before introducing more complex behaviours.

09 / TRAINING TOOL

Making the learning process visible and controllable.

I also built an in-engine tool for managing and observing the training process. The goal was to make the otherwise opaque interaction between the simulation and learning system easier to inspect while iterating.

TRAINING / SIMULATION TOOL

Training runs on a background thread because the Python PPO round-trip can otherwise block the Unreal editor. The visualizer uses a periodic policy snapshot so that observing the creature does not reintroduce the same synchronization problem.

11 / DEBUGGING

When the creature falls, find out why.

A major part of the project became understanding failures that appeared as simple "the creature fell over" problems.

One particularly important bug came from forward kinematics: the bone rotation offset relative to its parent was being dropped. This caused the creature to spawn in the wrong orientation and led to several follow-up assumptions about root orientation and height.

Other failures came from incorrect joint conventions, NaN values escaping fall detection, stale state surviving resets, and unit mismatches between Unreal's centimetre-based system and SI-based physics references.

These failures pushed the project toward a more explicit validation methodology instead of relying on parameter tweaking and visual judgement.

14 / WHAT I LEARNED

The hard part was not just writing the solver.

Building the project taught me that technical animation sits between several disciplines. The system needs to make sense mathematically, behave physically, remain fast enough to simulate, and still be controllable through useful tools.

More importantly, I learned to treat debugging as an experimental process: formulate a hypothesis, design a test that can actually distinguish it, and only then change the system.

15 / WHAT'S NEXT

From standing to locomotion.

The immediate goal is to demonstrate a stable learned standing behaviour. From there, the learning objective can progress toward weight shifting, stepping and eventually locomotion.

A second direction is runtime deployment, connecting the training representation to Unreal's production-side systems through Chaos and Control Rig.
